# ADR 0001: 共有D1内の家計データを世帯IDで分離する

日付: 2026-09-05。状態: 採用、段階実装中。関連: [Issue #102](https://github.com/yosket87/score-splitter/issues/102)。

## 背景

現行アプリは共有パスワードまたはパスキーによる既存1世帯の利用を前提とする。家計テーブルには所属列がなく、月・レコードIDだけで検索する。AIの実行guardとsource revisionはDB全体の単一行、振込revisionは月単位のため、明細に所属列を付けるだけでは分離できない。

通常経路はNext.js/OpenNext WorkerからD1への直接呼出し。旧HTTP Workerは切り戻し用に残り、モックはHTTP契約を利用する。これらを同じ認可契約に揃える。

## 判断

1世帯を1テナントとし、共有D1の家計・所属データに `household_id` を持たせる。認証済みサーバー処理だけが世帯コンテキストを発行し、データアクセス関数は必須引数で受け取る。

| 比較案 | 評価 |
|---|---|
| 共有D1＋世帯列 | 現行構成を維持でき、既存データを段階移行できる。すべてのSQL・制約・状態に世帯を適用する責任が必要。採用 |
| 世帯ごとにD1 | DBそのものを境界にできるが、DBの作成・binding・migration・復元の管理を世帯数に応じて増やす。現段階では選ばない |
| 別DB製品へ移行 | 現行のD1トリガー・batch・運用を同時に置き換える変更が大きい。現段階では選ばない |

複数DBへの分割は、実測負荷をもとに判断するIssue #118に残す。

## 認証と認可

- 世帯ID、将来の個人ID、家計上の `husband / wife` は別概念とする。今回Google認証やmembershipsを追加しない。
- 既存世帯をmigrationで明示作成する。共有パスワード成功時は既存認証識別子を持つ世帯を明示的に解決する。不明な所属を既存世帯へ代入する汎用fallbackは設けない。
- 既存セッション・パスキーの所属を補完し、token・credential ID・公開鍵・counterは保持する。パスキー署名検証後は、そのcredentialが所属する許可済み世帯のセッションを作る。
- `requireHouseholdContext()` は有効なセッションと実在する世帯を確認する。世帯なし・不明世帯・期限切れは拒否する。Cookieの形式確認は認可の代わりにしない。
- FormData、URL、JSON、任意ヘッダーの世帯IDは認可の根拠にしない。サーバー発行のコンテキストからのみデータ操作先を決定する。
- 家計の取得・更新・削除には世帯とレコードIDを同時に指定する。他世帯IDは不存在と同じ失敗になり、存在や内容を漏らさない。
- 家計の担当者変更は既存仕様のまま維持する。家計レコードを別世帯へ移す操作は提供しない。
- Next.jsの認証ガイドに従い、各Server Actionとデータアクセス層で認可を行う。画面やlayoutの非表示だけで保護しない。

## 認証前の処理

セッションのtoken検索は、世帯を知るための認証境界なので世帯引数を要求しない。ただし検索成功だけでは不十分で、期限と所属を検証する。

認証前のcredential解決・認証challenge・ログイン試行制限は家計APIから分離する。credentialの検索結果をそのまま画面へ返さず、署名検証の内部処理に限定する。登録challengeとパスキー管理は認証済み世帯を必須にする。

旧HTTPの家計処理は内部Bearerに加えて有効なセッショントークンを要求する。Bearerを持つだけの通常家計リクエストには応答しない。認証発行の内部制御経路と、公開LPのwaitlist処理は、それぞれの検証契約を維持する。

## データ・実行制御・クライアント状態

- 明細・月一覧・精算・CSV・コピー・振込履歴は同じ世帯の入力だけから作る。金額の符号・丸め・CSV形式を変更しない。
- 繰越の一意制約は現行の月・ラベル・金額・担当者に世帯を追加する。
- AI結果は世帯＋月。guard・UTC日次回数・cooldown・source revisionは世帯単位。既存のrevision対象列を維持し、AI分類列更新で自分の診断を無効にしない。
- 振込のoperation IDは世帯内で一意。台帳の参照は複合FKで同一世帯を保証し、履歴の追記専用とsnapshot不変を維持する。
- 永続データキャッシュは追加しない。再取得でも毎回認可し、React key・非同期応答・振込のsessionStorageを世帯＋月で分離する。セッショントークンはクライアントへ渡さない。

## 移行と運用

追加、既存データ補完、利用切替、制約強化の順で移行する。旧版と新schemaが共存する期間は既存1世帯だけとし、旧版の書込で生じたNULLを切替停止中に追補する。恒久的な既存世帯DEFAULTは設けない。

切替中は旧HTTP・Previewを含む旧版からの読書きと新しい認証発行を止め、AI実行を終了させる。台帳の補完/再構築はmigration内で更新禁止トリガーを扱い、保護が外れた状態を公開しない。migrationによる明細の再構築ではrevisionを進めず、保存済み値を保持する。通常の月コピーによる明細追加・削除は、その世帯のrevisionを進める。

制約とキーを切り替えた後のrollback先は世帯対応版に限定する。DB復元は別操作であり、復元点以降の記録への影響を提示した明示承認なしに行わない。各段階のmigrationは配布単位を分け、全pending適用による早期切替を防ぐ。

本番は既存世帯のみを継続提供する。2世帯の検証はローカルD1と隔離した開発D1で行い、旧Previewが共有DBを読み出せる状態を作らない。

## 検証

2世帯・同月・同内容・同operation IDのfixtureで、通常経路・直接ID指定・コピー・AI・振込・HTTP・mock・CSV・クライアント状態の非干渉を検証する。既存token・credential・件数・金額・精算・台帳JSON・revisionを移行前後で照合する。

実D1の全migration、FK/一意制約/トリガー、書込batch失敗時の原子性、バックアップ復元後の実関数を検証する。FakeのSQL文字列認識だけを分離の証拠にしない。
