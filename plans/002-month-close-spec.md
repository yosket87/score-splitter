# 振込前・振込済みの状態表示仕様

更新日: 2026-09-05。起点: 最新取得済みmain `bcb51ff`（精算内訳表示 #100 を含む）。ファイル名は参照互換のため維持する。

ユーザーの補足により、主目的を「月の編集禁止」から「振込前・振込済みを分かりやすくする」へ変更した。本書は従来の月締め案を置き換える。機能実装・ローカル検証済み。本番DB変更・デプロイは未実施。

## 目的と範囲

今月いくら振り込む必要があり、すでに振り込んだかを表示する。振込済みでも収入・支出・繰越を編集できる。アプリから銀行送金は行わず、利用者が実際に振り込んだことを記録する。

編集ロック、月のopen/closed、再開操作、コピー先拒否、双方承認は導入しない。既存CRUD・コピー・CSV・AI分類は利用を継続する。未入力管理、通知、銀行接続も対象外。

## 状態表示

月の固定フラグだけでなく、現在の精算目標と有効な振込履歴から表示を導出する。

| 条件 | 表示 | 主な操作 |
|---|---|---|
| 有効な振込記録なし、目標が非0 | 振込前 | 「振込済みにする」 |
| 有効な振込記録あり、残額0 | 振込済み | 記録日・金額・履歴を確認 |
| 有効な振込記録あり、残額が非0 | 振込済み・差額あり | 「差額を振込済みにする」 |
| 有効な振込記録なし、目標0 | 振込不要 | 記録操作なし |

「差額あり」は第三の月締め状態ではなく、振込済み記録に添える注意表示。振込後の編集で過去の支払を自動取消ししない。差額がなくなる編集なら振込済み表示を維持する。取消のみの履歴は有効な振込記録に数えない。

## 画面仕様

既存の黒い精算額・青い方向表示・精算内訳・担当者色・グラフ・ガラス背景を維持する。375pxは1カラム、デスクトップは左要約／右明細。

- 要約の精算額付近に「振込前」「振込済み」と支払日を表示する。初回は既存精算額が振込対象額。
- 振込済み後も現在の精算額と内訳は編集に応じて更新する。「振込済み額」と「残りの振込額」を区別する。
- 差額ありでは追加額と方向を明示し、以前の全額を再振込する案内にしない。逆方向なら「妻→夫へ5,500円の差額精算が必要」のように具体的に表示。
- 「振込済みにする」でサーバーの最新見積りを取得。金額・方向・支払日を確認し「振込済みとして記録」。実際の振込は行わないと説明する。
- 支払日は日付のみYYYY-MM-DD。Asia/Tokyo当日を初期値とし、実在日・未来日でないことを検証。処理日時はUTC。
- 誤って押した場合は「振込済みの記録を取り消す」。実際の送金・返金は行われないことを説明する。理由を入力し履歴は残す。
- 実際の支払額や日付の誤記は「記録を訂正」で取消＋正しい実支払の置換。取消で実際の返金を代用しない。
- 一覧の追加・編集・削除・フラグ・コピーを無効化しない。開き直しの確認も出さない。
- 取得失敗を0円扱いせず再取得を案内。送信中は連打を抑止し、応答消失は同じ操作キーで結果確認する。
- キーボード操作、フォーカス復帰、エラー読み上げを既存ダイアログに合わせる。

## 計算・端数・編集後の差額

既存calculateSettlementは変更しない。理論精算Sの符号は夫→妻が正。整数目標Tは絶対値の切捨て（負の0を0へ正規化）。有効な振込の符号付き合計Pに対し、残額D=T-P。

| 例 | T | P | D／表示 |
|---|---:|---:|---|
| 初回 | 15,500 | 0 | 夫→妻15,500、振込前 |
| 記録直後 | 15,500 | 15,500 | 0、振込済み |
| 編集で目標増加 | 20,000 | 15,500 | 夫→妻4,500、差額あり |
| 編集で目標減少 | 10,000 | 15,500 | 妻→夫5,500、差額あり |
| 編集で方向逆転 | -10,000 | 15,500 | 妻→夫25,500、差額あり |
| 編集で目標0 | 0 | 15,500 | 妻→夫15,500、差額あり |
| 初めから目標0 | 0 | 0 | 振込不要、記録操作なし |
| 記録を誤操作として取消 | 15,500 | 0 | 振込前へ戻る、取消履歴は残る |
| 記録15,500を実額15,000へ訂正 | 15,500 | 15,000 | 夫→妻500、差額あり |

夫収支101・妻0ではS=50.5、T=50。支払後は夫51・妻50。逆方向は妻に1円多く残る。最新mainの精算内訳は0.5円を表示するので、記録額との違いを端数説明で示す。自動の次月繰越はしない。

明細の各集計途中和、H+W、H-W、T-Pの安全整数を確認し、S=(H-W)/2との一致を確認する。S自体には半整数を許可する。支払合計PはBigIntで正確に集計してから最終値の安全整数を検証し、履歴の並び順による精度喪失を防ぐ。記録は非0の整数円。差額0の支払行は作らない。部分支払の新規登録は今回対象外だが、誤記訂正は実額へ直せる。

## 保存するデータ

- `month_payment_revisions`: month PK、revision非負整数。月ごとの明細変更・振込記録変更を検知するための番号。編集可否を表す状態は持たない。
- `payment_operations`: UUIDの冪等キーPK、month、kind(record/correct/void)、expected_revision、正規化入力、結果JSON、記録者person nullable/authMethod、UTC日時。認証トークンは保存しない。
- `payment_records`: id PK、operation_id UNIQUE、month、signed_yen、paid_on、UTC記録日時、記録時の入力とCalculationResultのsnapshot_json、計算・丸めバージョン。
- `payment_voids`: id PK、operation_id UNIQUE、payment_id UNIQUE、理由、UTC日時。取消は元記録を削除せず、有効額の合計から除外する。置換支払は同一訂正操作に紐づく別のpayment_records行。

snapshotは当時の明細ID・項目名・金額・担当者・フラグ・作成日時を含む。過去の支払額の根拠を現データから再計算しない。通常画面は現在データを表示し、snapshotは履歴詳細から見る。履歴テーブルの確定後UPDATE/DELETEは拒否するが、家計明細には拒否トリガーを置かない。

既存月は履歴なし・P=0。空月は仮想revision=0。`Session.person=null` は「共有ログインによる記録」とし、夫・妻の承認とは表現しない。コピー先へ振込状態・振込記録はコピーしない。後続月を自動変更しない。

## API・認証

通常はServer Actions → `src/lib/api/payment-status.ts` → 共有D1関数。モックと旧HTTP経路の契約も揃える。

| API | 入力・結果 |
|---|---|
| GET /months/:month/payment-status | revision、現在の計算、T/P/D、導出表示、履歴 |
| POST /months/:month/payments | operationId、expectedRevision、confirmedSignedYen、paidOn。サーバー再計算Dと照合して記録 |
| POST /months/:month/payment-corrections | operationId、expectedRevision、paymentId、reason、replacement:null またはsignedYen/paidOn |
| GET /months/:month/payment-operations/:id | 冪等な結果照会 |

すべて認証必須。actorは検証済みセッション由来。旧HTTP更新も内部トークンに加えて有効セッションを検証する。ZodでUUID、既存有効月、安全整数、日付、理由1〜500字、strict bodyを検証。

400は不正入力、401未認証、404不存在、409は古い確認情報・同じキーで異内容・二重取消、500は障害。既存HttpError→ApiError→ActionResultへ安全な日本語で変換。成功時に対象月・年を再検証する。

## 同時編集と二重登録

編集は禁止しないが、確認画面を開いてから金額が変わった際に誤った振込額を記録しないよう整合性は維持する。

1. 明細・月revision・振込台帳を同一読取batchで取得し、Dをサーバー計算。
2. 認証・基本形式検証後、保存済み冪等キーを先に照合。同じ内容なら現在のrevisionに関係なく当時の結果を返す。
3. 新規操作は単一D1 batchでrevision一致を検査する操作INSERT、振込/取消行INSERT、revision加算を実施。不一致はトリガーのRAISE(ABORT)で全体rollback。重複キーの失敗後は保存済み結果を再読込して照合する。
4. 3明細のINSERT/UPDATE/DELETEのAFTERトリガーでrevisionを増やす。OLD/NEWのDB上のmonthを使い、金額以外のsnapshot対象変更も検知する。既存AI用revisionは用途・対象列が異なるため流用しない。
5. 編集が先なら記録409で再確認。記録が先なら編集は成功し、次の取得で差額ありを表示。編集を拒否する方式とはここが異なる。

コピーも既存の明細トリガーでrevisionを更新する。コピー処理へのopen検査・assertionテーブル・専用のコピー競合強化は追加しない。AI分類だけの変更はsnapshot対象外で、月の振込revisionを更新しなくてよい。

公式根拠: [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) の全体rollbackを利用する。以前の設計スパイクでbatch rollbackと競合時の条件検査はローカルD1で確認したが、本改訂の振込ドメインも全migrationを適用した一時D1で、CRUD・コピー・同時編集・同一キー再送・rollbackを実関数で検証済み。
