# AI家計診断 MVP 設計

## 概要

ヤマワケの月次家計データをAIが振り返り、過去の自分たちとの比較に基づいて、支出の変化・良かった点・見直し候補を提示する。

診断は夫婦を比較・評価するものではない。夫婦を一つのチームとして扱い、家計について話し合うための共通材料を提供する。

## 目的

- 選択月の支出が普段とどう違うかを短時間で把握できる
- 増加した支出について、根拠となる金額と一緒に確認できる
- 生活を責めるのではなく、翌月に試せる見直し候補を得られる
- 良かった変化も示し、継続的な振り返りを支援する

## プロダクト原則

1. **夫婦はチーム**: 個人別の優劣や責任を示さず、家庭全体を対象にする
2. **数字には率直、人には穏やか**: 数値変化は明確に伝え、人物や生活を評価しない
3. **過去の自分たちと比較**: 世間一般や他家庭の平均を「適正」として使わない
4. **根拠を表示**: 指摘には金額差・増減率・比較期間を添える
5. **問題を作らない**: 有意な変化がなければ、その事実をそのまま伝える
6. **AIは助言のみ**: 収入・支出・繰越データをAIが自動変更しない

## MVPスコープ

### 含めるもの

- 選択中の月を対象とするオンデマンド診断
- 選択月と直前3か月平均との比較
- 初回診断時の支出カテゴリ自動分類
- 分類結果の内部保存と再利用
- 家庭全体を対象とした4ブロックの診断結果
- 診断結果の保存と再表示
- 元データ更新後の期限切れ表示と手動再診断
- 比較データが不足する場合の段階的な表示

### 含めないもの

- 夫・妻の個人別診断や比較
- 他家庭・世間一般との比較
- カテゴリ別予算の設定
- 通常画面でのカテゴリ表示・編集
- AIとの自由チャット
- 全期間診断、前年同月比較
- 毎月の自動診断や通知
- 投資・保険・税金などの金融助言
- AIによる家計データの追加・編集・削除

## ユーザー体験

### 起点

月次画面の精算結果付近に「AIで今月を振り返る」ボタンを配置する。診断は自動実行せず、ユーザーの明示操作で開始する。

初回診断では次の進行状態を表示する。

1. 支出を整理しています
2. 過去の傾向と比較しています
3. 振り返りを作成しています

モバイルではボトムシート、デスクトップではダイアログを使用し、既存のレスポンシブなモーダルパターンに合わせる。

### 診断結果

長文レポートではなく、次の4ブロックを表示する。

1. **今月のまとめ**: 支出総額と過去平均からの変化
2. **気になった変化**: 有意に増加したカテゴリを最大3件
3. **良かった点**: 減少または安定している項目
4. **来月のヒント**: 過去の水準を参考にした具体的な見直し候補

各指摘には、アプリが計算した金額または増減率を根拠表示として添える。数値はAI文章の一部にせず、検証済みデータとしてUIで組み合わせる。

節約可能額はAIに計算させない。アプリが計算した「過去平均まで戻した場合の差額」を、削減を保証しない「削減余地」として表示する。

### 保存済み結果

月ごとに最新の診断結果を1件保存し、再表示時はAIを呼ばずに表示する。

診断後に対象月または比較対象月のデータが変わった場合は、保存済み結果を残したまま次の案内を表示する。

> 家計データが更新されています。最新の内容で再診断してください。

再診断はユーザーが明示的に実行する。バックグラウンドで勝手にAIを呼ばない。

## 比較範囲

選択月を基準月とし、その直前3か月を比較対象にする。

| 利用可能な過去月 | 挙動 |
|---|---|
| 0か月 | 今月の支出構成のみ説明し、増減評価は行わない |
| 1〜2か月 | 利用可能な月の平均と比較し、「参考値」と明記する |
| 3か月 | 直前3か月平均との通常診断を行う |

データが存在しない月は平均の分母に含めない。ただし、月自体に支出が0件なのか取得障害なのかを区別し、取得障害時は診断を開始しない。

## 支出カテゴリ

カテゴリはUIに表示しない内部情報とし、固定された候補からAIに選択させる。AIによる自由なカテゴリ生成は許可しない。

| 内部値 | 意味 |
|---|---|
| `groceries` | 食費 |
| `dining` | 外食 |
| `household` | 日用品 |
| `housing` | 住居 |
| `utilities` | 水道・光熱 |
| `communications` | 通信 |
| `transportation` | 交通 |
| `healthcare` | 医療・健康 |
| `clothing_beauty` | 衣服・美容 |
| `entertainment` | 娯楽 |
| `subscriptions` | サブスク |
| `social_gifts` | 交際・贈答 |
| `travel` | 旅行 |
| `other` | その他 |

診断対象4か月に含まれる未分類支出を、正規化したラベル単位でまとめて分類する。同じ正規化ラベルには同じカテゴリを適用する。分類に成功した結果だけを支出レコードへ保存し、以後の診断で再利用する。

入力時の自動分類、通常画面でのカテゴリ表示、ユーザーによる修正は将来拡張とする。

## 診断対象データ

### 支出

- `isCarryover = false` の実支出をカテゴリ比較の対象にする
- 繰越扱いにした支出は、当月の実支出から除外する
- 支払者の `person` は診断集計およびAI入力に含めない

### 繰越

- 未清算繰越は「確認事項」として合計額だけ扱う
- 繰越を浪費や使いすぎと評価しない
- 清算済み繰越を当月の新規消費としてカテゴリ集計しない

### 収入

- 世帯全体の合計額のみを利用できる
- 収入ラベルと個人別金額はAI入力に含めない
- 個人の収入差を評価や助言に使用しない

## 診断候補の抽出

異常検出と金額計算はアプリ側の決定的なロジックで行う。AIに自由な計算や候補抽出を任せない。

### 増加候補

カテゴリが次の両方を満たす場合に、気になった変化の候補とする。

- 過去平均との差額が3,000円以上
- 過去平均からの増加率が20%以上

候補は差額の大きい順に最大3件とする。過去平均が0円の場合は増加率を算出せず、新規または一時的な支出として別扱いにする。

### 良かった点

減少額と減少率が同じ基準を満たすカテゴリ、または3か月にわたって安定している主要カテゴリから候補を作る。数値的根拠がある場合は1件以上提示し、該当候補がなければ無理に生成しない。

### 見直し候補からの除外

- `healthcare` は原則として削減候補にしない
- 一度だけ発生した高額支出を継続的な使いすぎと断定しない
- 支出目的が不明な `other` には断定的な助言をしない
- 3,000円・20%未満の小さな変動を主要問題として扱わない

しきい値は内部設定として一元管理し、利用状況を見て変更可能にする。MVPではユーザー設定にしない。

## AIの責務と境界

### AIへ任せること

- 自由入力ラベルを固定カテゴリへ分類する
- アプリが抽出した候補の中から、説明価値の高い項目を選ぶ
- 数値根拠を使い、短く読みやすい診断文へ変換する
- 夫婦チームの共同意思決定につながるヒントを提案する

### AIへ任せないこと

- 合計、平均、増減率、削減余地の計算
- 夫・妻の比較や責任判定
- 医療・金融上の専門的助言
- 家計データの更新
- 固定候補外のカテゴリ生成
- 根拠のない問題や節約可能額の生成

AIプロバイダーは、サーバー側から構造化出力を要求できるインターフェースの背後に隔離する。モデル名はサーバー環境設定で管理し、UIや診断結果の契約を特定モデルへ依存させない。

## データフロー

1. サーバーが選択月と直前3か月の収入・支出・繰越を取得する
2. 取得結果を検証し、未分類の実支出ラベルを抽出する
3. 未分類ラベルだけをAIへ送り、固定カテゴリの構造化結果を受け取る
4. スキーマ検証に成功した分類だけをDBへ保存する
5. アプリ側でカテゴリ別合計、過去平均、差額、増減率、削減余地を計算する
6. 決定的なルールで診断候補を抽出する
7. 集計値、候補、主要因となるラベルだけをAIへ送る
8. 4ブロックの構造化診断結果を受け取って検証する
9. 入力指紋とともに診断結果を保存し、UIへ返す

分類に成功した後で診断生成に失敗した場合、分類結果は保持する。次回は分類を再実行せず、診断生成から再開できる。

## データモデル

### `expenses` への追加

| カラム | 型 | 説明 |
|---|---|---|
| `ai_category` | TEXT NULL | 固定カテゴリの内部値 |
| `ai_category_source` | TEXT NULL | MVPでは `ai` のみ |
| `ai_categorized_at` | TEXT NULL | 分類日時 |

既存レコードは未分類のまま移行し、最初の診断時に必要な範囲だけ分類する。一括バックフィルは行わない。

### `ai_diagnoses`

| カラム | 型 | 説明 |
|---|---|---|
| `id` | TEXT | 主キー |
| `month` | TEXT UNIQUE | 診断対象月（YYYYMM） |
| `result_json` | TEXT NULL | 検証済みの4ブロック診断結果。初回実行リース中はNULL |
| `input_hash` | TEXT NULL | 診断入力の安定した指紋 |
| `analysis_version` | TEXT NULL | 集計・プロンプト契約のバージョン |
| `run_token` | TEXT NULL | 同時実行を抑止する一時トークン |
| `run_expires_at` | TEXT NULL | 実行リースの期限 |
| `created_at` | TEXT | 初回作成日時 |
| `updated_at` | TEXT | 最終診断日時 |

MVPでは月ごとに最新結果1件をupsertし、診断履歴は保持しない。

診断開始時は、D1の条件付き更新で対象月の実行リースを取得する。リース取得に失敗した要求はAIを呼ばず、「診断を実行中です」と返す。異常終了でトークンを解放できない場合に備え、リースは2分で失効する。診断結果の保存とリース解放には、取得時と同じ`run_token`を要求する。

`input_hash`は、対象4か月の診断に関係するレコードを安定順に並べ、月・種別・ID・ラベル・金額・繰越状態・カテゴリから生成する。対象月または比較月の入力が変われば期限切れになる。表示専用情報や個人別の担当者は指紋に含めない。

## 診断結果の契約

AIからは自由文1本ではなく、次の構造を受け取る。`candidateId`はアプリが生成した候補だけを参照でき、AIは金額を返さない。

```typescript
interface AiDiagnosisResult {
  summaryText: string
  notableChanges: Array<{
    candidateId: string
    commentary: string
  }>
  positivePoints: Array<{
    candidateId: string
    commentary: string
  }>
  suggestions: Array<{
    candidateId: string
    commentary: string
  }>
  dataSufficiency: 'current_only' | 'reference' | 'full'
}
```

保存前に、すべての`candidateId`がアプリから渡した候補に含まれることを検証する。UIは候補IDからカテゴリ、差額、増減率、削減余地を取得し、AIの説明文とは別の根拠表示として描画する。これにより、AIによる数値の計算・転記ミスを防ぐ。

## 文体と安全ルール

- 「夫」「妻」を主語にした評価を生成しない
- 「浪費」「無駄遣い」「責任」など対立を生む表現を使わない
- 「削るべき」と命令せず、「見直し候補」「振り返る余地」と表現する
- 生活の楽しみを否定せず、意図した支出か確認する形にする
- 医療費の削減を促さない
- 削減効果を保証しない
- データ不足時に断定しない
- 有意な変化がなければ「大きな変化はありません」と返せる

支出ラベルは命令ではなくデータとして扱う。ラベル内の文章をプロンプト指示として解釈しないよう、構造化したデータ領域に隔離する。

## プライバシーとセキュリティ

- AI APIキーはサーバー環境だけで保持し、ブラウザへ公開しない
- AI呼び出しはServer Actionまたはサーバー専用モジュールから行う
- 分類時は未分類の支出ラベルだけを送る
- 診断時はカテゴリ集計、変化候補、必要最小限の主要ラベルだけを送る
- レコードID、担当者、収入ラベル、Cookie、認証情報を送らない
- AIプロバイダー側でAPI入力を学習に使用しない契約・設定を採用する
- AI応答は信頼せず、固定スキーマと許可カテゴリで検証する
- 文字数と件数に上限を設け、過大入力とプロンプトインジェクションの影響を抑える

## エラー処理

| 状況 | 挙動 |
|---|---|
| 選択月に実支出がない | 診断を実行せず、対象データがないことを案内 |
| 過去データが0〜2か月 | 利用可能な範囲で診断し、データ充足度を明示 |
| 家計データ取得失敗 | AIを呼ばず、通常の再試行エラーを表示 |
| カテゴリ分類失敗 | 未検証結果を保存せず、診断全体を再実行可能にする |
| 診断形式が不正 | サーバー側で一度だけ再試行し、再失敗時はエラー表示 |
| 診断サービス停止 | 保存済み診断があれば表示し、新規実行だけ失敗として案内 |
| 診断後に元データが変更 | 保存済み結果を期限切れ表示にし、手動再診断を案内 |

AI処理の失敗によって、既存の収入・支出・繰越データを変更または削除してはならない。

## コストと実行制御

- 初回は分類と診断生成の最大2回を実行する
- 以後は未分類ラベルがある場合だけ分類を実行する
- 保存済みで入力指紋が一致する場合はAIを呼ばない
- 同じ月に対する同時診断をサーバー側で抑止する
- ラベルを重複排除し、分類入力件数を減らす
- 分類と診断で異なるモデルを利用できる抽象化を設ける
- タイムアウトを設定し、画面を無期限に待機させない

## テスト方針

### ユニットテスト

- カテゴリ別集計、過去平均、増減額、増減率
- 過去平均0円の場合の扱い
- 3,000円・20%の候補抽出境界
- 候補最大3件と並び順
- 医療・健康カテゴリの削減候補除外
- 繰越支出と清算済み繰越の除外
- 安定した入力指紋と変更検知
- 個人別担当者を診断入力へ含めない変換

### 統合テスト

- 未分類ラベルだけを分類する
- 許可外カテゴリを拒否する
- 検証済み分類だけを保存する
- 分類成功後に診断が失敗しても分類を保持する
- 構造化診断結果の検証と保存
- 保存済み診断の再利用
- 元データ変更後の期限切れ判定
- 同一月への同時実行抑止

AI応答は固定レスポンスへ差し替え、実サービスへ依存しない再現可能なテストにする。

### コンポーネント・E2Eテスト

- 初回診断の進行状態
- データ不足時の表示
- 4ブロックの診断結果表示
- 保存済み診断の即時表示
- 期限切れ表示と再診断
- AI障害時に既存の月次画面を継続利用できること
- 診断表示に夫・妻の比較が含まれないこと

## 受け入れ条件

1. 選択月に実支出があれば、ユーザー操作で診断を開始できる
2. 初回診断で未分類支出が固定カテゴリへ分類され、内部保存される
3. 選択月と最大3か月分の過去平均をアプリ側で正しく比較する
4. 診断結果に金額または増減率の根拠が表示される
5. 診断結果が家庭全体を対象とし、個人の責任や優劣を示さない
6. 有意な問題がない場合、AIが問題を捏造しない
7. 保存済み診断を追加のAI呼び出しなしで再表示できる
8. 元データ変更後、保存済み診断が期限切れと判定される
9. AI障害が収入・支出・繰越データや既存の精算機能へ影響しない
10. AIへ送信される情報に担当者、収入ラベル、認証情報が含まれない

## 将来拡張

- 支出登録後のバックグラウンド分類
- 通常画面へのカテゴリチップ表示と手動修正
- ラベルとカテゴリの世帯内対応表によるAI呼び出し削減
- 全期間トレンド診断
- 前年同月比較による季節性への対応
- カテゴリ別予算との比較
- 月次診断の通知

これらはMVPの利用状況と診断品質を確認してから、個別に設計する。
